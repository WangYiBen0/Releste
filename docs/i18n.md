# Editor internationalisation (i18n) and localisation (l10n)

Status: implemented. Owner: `crates/editor` (loader) and `locales/` (data).
Audience: maintainers of the editor, and anyone adding a language.

This document is the design rationale and the runtime contract. If you only
want to add a language, read [CONTRIBUTING-i18n.md](../CONTRIBUTING-i18n.md)
instead - you do not need anything from this file to do that.

---

## 1. What this is

The Releste map editor's user interface is translated through small
human-readable TOML catalogs:

```text
locales/en_US/editor.toml    <- source of truth for keys and English strings
locales/zh_CN/editor.toml    <- Simplified Chinese (UTF-8)
```

The catalogs are **runtime data**. They are read from disk when the editor
starts (or when the language is switched) with `std::fs::read_to_string`,
parsed with the `toml` crate, and stored in a flat `HashMap<String, String>`.

They are **never compiled into the binary**. There is no `include_str!`, no
`include!("../locales/en_US/editor.toml")`, and no build-script codegen. This
is not an implementation detail; it is the same rule the rest of the project
follows for `plugins/`, `resources/` and `libs/` (AGENTS.md section 3:
"Nothing here may be compiled into the binary"). A translator must be able to
fix a string without a Rust toolchain, and a shipped build must be able to pick
up an updated catalog without being rebuilt.

### 1.1 Consequences you should be aware of

- A missing catalog is **not** a build error and **not** a fatal startup error.
  It degrades: see the fallback chain in section 4.
- A malformed catalog (bad TOML, wrong value type) is a warning, not a panic.
  AGENTS.md section 15.8 forbids panicking; the loader returns `Result` and the
  caller logs with `tracing::warn!`.
- Because catalogs are not statically checked, a key typo shows up as the key
  ID rendered in the UI plus a `tracing::warn!`, not as a compile failure.
  That is the deliberate trade: no build-time safety, in exchange for
  translator access and hot-swappable languages.

## 2. Why not Fluent, gettext, or rust-embed

AGENTS.md section 15.1: **do not add new crates** unless they are already in
`[workspace.dependencies]`, or an issue has been opened to discuss it.

The relevant existing dependencies in `crates/editor/Cargo.toml` are:

| Crate | Already used for |
|---|---|
| `toml` | `.map` sidecars, config, and now catalogs |
| `serde` | deriving the catalog struct |
| `thiserror` | the loader's error type |
| `tracing` | warnings on missing/malformed keys |
| `clap` | the `--lang` flag |

That is a complete i18n toolkit for the scope the editor actually has. Adding
one of the alternatives would cost a new dependency without buying anything:

- **Fluent (`fluent`/`fluent-bundle`)** is the right tool for
  morphological languages - plural categories, grammatical gender, case
  agreement. The editor's strings are menu labels, tool names, panel headings,
  and short status lines. There is no plural-sensitive copy and there are no
  gendered sentences. Adopting Fluent would mean a new parser, a new file
  format (`.ftl`), and a new selector syntax, to solve problems the editor
  does not have.
- **gettext (`gettext-rs`)** binds `libintl`. That is a C dependency at build
  and link time, it does not fit the pure-Rust cross-platform story (Windows,
  macOS, and potentially Wasm per AGENTS.md section 1), and it would put the
  catalogs through `msgfmt` into `.mo` binaries - i.e. compiled in, which is
  exactly what section 1 forbids.
- **`rust-embed`** solves loading, not translating: it would embed the
  catalogs into the executable, defeating runtime loading.

### 2.1 What we would lose by hand-rolling

Honest accounting, because the choice is a trade and not a free win:

- No plural rules. If the editor ever needs "1 entity selected" vs
  "5 entities selected", that needs either two keys
  (`status.selection.one` / `status.selection.many`) or a code-side branch.
  Two keys is the plan of record; it stays within the flat model.
- No ICU plural/gender/select, no date or number formatters.
- No translator tooling ecosystem (Poedit and friends do not read TOML).
- No compile-time key checking.

If a future requirement breaks the flat model - for example a language needing
grammatical case driven by the surrounding sentence - that is the signal to
reopen section 15.1 with an issue, the same way AGENTS.md's final note says:
open an issue rather than bypass the rule.

## 3. Runtime directory layout

```text
Releste/                       # or the installed tree, next to the executable
|-- locales/
|   |-- en_US/
|   |   `-- editor.toml        # source of truth for keys + English strings
|   `-- zh_CN/
|       `-- editor.toml        # Simplified Chinese, UTF-8, non-ASCII by nature
`-- (crates/, tools/, ...)
```

Rules:

- One directory per locale. The directory name **is** the locale tag, and it is
  used verbatim as the value of `--lang` / `editor.lang`.
- Locale tags are `<language>_<REGION>` with a lowercase language and an
  uppercase region: `en_US`, `zh_CN`, `ja_JP`, `pt_BR`, `de_DE`. This is the
  POSIX/BCP-47-flavoured form users of game tooling already expect, and it keeps
  directory names case-sensitively unambiguous. `en` or `en-GB` are not used;
  a language with no meaningful regional split still gets a region, chosen by
  the first contributor (`ja_JP` is the obvious default for Japanese).
- The catalog file inside a locale directory is always named `editor.toml`.
  The editor ships more than one surface eventually (the game's own UI, the
  CLI); when that happens each surface gets its own `<surface>.toml` in the
  same locale directory, and `editor.toml` continues to mean "the editor".
- Catalogs live **outside** `crates/`. Localisation data is explicitly the one
  exception to the ASCII rule in AGENTS.md section 5.4, and section 7 below
  shows how the repository's lint gate already encodes that exception.
- The path is resolved relative to the executable / repository root the same
  way `plugins/` and `resources/` are, never as a hard-coded absolute path
  (AGENTS.md section 3).

Note that .gitignore does not exclude `locales/` - catalogs are tracked source
data, they are just not tracked *code*.

## 4. Fallback chain

Lookup is a straight resolution order, evaluated per key, not per catalog.
The first of these that produces a hit wins:

```text
1. active locale catalog      locales/<active>/editor.toml     (exact key)
2. en_US catalog              locales/en_US/editor.toml        (exact key)
3. the key ID itself          e.g. the literal text "menu.file.save"
```

Design notes:

- **Step 2 is unconditional.** `en_US` is the source of truth. A language that
  only translates 60% of the keys is a completely valid contribution: the other
  40% render in English rather than breaking the UI. This is why
  `en_US/editor.toml` must never be missing a key that any code path uses, and
  why it is the file that key-set checks compare against.
- **Step 3 is the failure mode that must stay visible.** A key that resolves to
  itself is a bug the developer should see immediately. Rendering
  `status.no_path` in the status bar is ugly on purpose - it is a louder
  signal than an empty label or a silently reused English string. The lookup
  also emits `tracing::warn!` with the key name so the developer can find it
  in the log without reading the UI.
- **`en_US` is not special-cased when it is the active locale.** Opening
  `--lang en_US` runs step 1 and succeeds there; the chain is only interesting
  for other locales.
- **No locale-aware folding.** `zh_CN` does not inherit from `zh`. There is no
  parent-locale resolution, no `zh_Hans` aliasing, and no script subtags. If a
  locale wants strings, the file must carry them. Keeping the chain three steps
  long keeps it debuggable by reading a few lines.
- **A catalog that exists but does not load** (bad TOML, unreadable, value is
  not a string) behaves exactly like a missing catalog: warn, then skip to
  step 2. It never takes the editor down.

### 4.1 Placeholders

Placeholders are the `{name}` form, substituted at render time:

```toml
status.rooms_loaded = "loaded {count} rooms"
```

- The placeholder **syntax** - the literal `{name}` fragment - is ASCII, so it
  survives in every catalog including non-ASCII ones.
- A **missing placeholder** in a translation is not an error and does not abort
  substitution. Substitution is unconditional: if the target string has no
  `{count}` token, the arguments are simply unused and the string renders
  without the number. Translators are therefore able to drop a placeholder
  deliberately when the number reads badly in their language, without breaking
  anything.
- A **placeholder name that does not match the call site** (e.g. `{n}` where
  the code passes `count`) is likewise not an error; the unmatched token
  renders literally as `{n}`. This is detectable by eye, and it is what the
  translation review rule exists to catch.
- A **missing key** follows the chain above and renders the key ID; placeholders
  are not applied to the fallback key ID.
- Placeholders are always ASCII identifiers. Never translate the name inside
  the braces - translate around it.
- Comments are never catalog entries. Only quoted `key = "value"` lines are
  loaded, so a `{name}` written inside a `#` comment is inert and never reaches
  the substituter.

## 5. Key naming convention

Keys are dot-separated, lowercase, and namespaced by **where the string appears**,
not by the widget type or by the module that draws it:

```text
<namespace>.<area>.<item>
```

Established namespaces:

| Prefix | Covers |
|---|---|
| `app.*` | application-level chrome: window title, quit confirmation, about |
| `menu.*` | menu bar and its entries, typically `menu.file.save` |
| `panel.*` | panel titles and tabs: `panel.rooms`, `panel.tiles` |
| `inspector.*` | the schema-driven entity inspector |
| `widget.*` | reusable control labels shared across panels |
| `status.*` | transient status-bar messages, usually with placeholders |
| `canvas.*` | messages drawn on the map canvas |
| `app.cli.*` | reserved; **not used** - clap help stays English (see section 6) |

Entity property names, enum choice values and Schema tooltips are **not**
localised. They are map data and developer-authored Schema metadata: a property
key like `facing` is written into the `.map` file, so translating it would
change the file format. The inspector shows them verbatim; only the chrome
around them (panel titles, `inspector.kind`, type-mismatch text) is translated.

Rules:

- A key ID is a **stable identifier**, not a string. Renaming a key is a breaking
  change for every catalog in the tree; it must be done in the same change as
  the call site and every catalog updated to match.
- Use short, structural segments (`menu.file.save`, not
  `menu_bar_file_menu_save_item`).
- Do not put English words that will need translating into a key name. If the
  string is a proper noun that is never translated (a file format name), it
  still gets a key, so its placement is consistent.
- Do not encode the source text in the key. `status.no_path`, not
  `status.pass_a_path_on_the_command_line`. The English lives in
  `en_US/editor.toml` and nowhere else.
- Prefer a new key over an existing key whose English happens to read the same
  today. Two screens that say "Open" today are free to diverge in another
  language tomorrow.

### 5.1 Checking that the key sets match

`en_US` and any other tracked catalog must have **identical key sets**. No key
is permitted in `zh_CN` that is absent from `en_US` (it would be dead), and no
key in `en_US` is permitted to be missing from `zh_CN` in CI-terms, although
missing keys degrade gracefully at runtime per section 4.

There is deliberately **no script under `crates/`** for this, because the check
is a property of the data and can be done without a Rust build:

```bash
# Keys present in en_US but not in zh_CN, and vice versa.
diff <(grep -oE '^"[a-z0-9_.]+"' locales/en_US/editor.toml | sort) \
     <(grep -oE '^"[a-z0-9_.]+"' locales/zh_CN/editor.toml | sort)
```

An empty diff is the goal. The editor also warns at startup when the active
catalog is missing keys relative to `en_US`, which catches it at run time as
well.

## 6. Selecting a language

Three sources, in precedence order:

1. **`--lang <tag>`** on the command line (the editor binary owns this flag).
2. **`lang = "..."`** in the editor's config file, if one is present.
3. **Default: `en_US`.**

The tag is the locale directory name, e.g. `--lang zh_CN`. An unknown tag is
not fatal: warn, then fall back to `en_US` through the chain in section 4.

Switching language at run time re-reads the catalog from disk. That keeps the
"no restart required" property consistent with the rest of the project, and it
is cheap: the whole catalog is a few kilobytes of text.

## 7. The ASCII gate, and why `locales/` is exempt

AGENTS.md section 5.4 requires **every tracked file to be ASCII-only**
(`0x00`-`0x7F`), with exactly one carve-out: "Localisation data is the only
exception, and it does not live in the source tree."

A Simplified Chinese catalog is genuinely non-ASCII UTF-8. This is a real,
by-design conflict and it is resolved by the rule itself, not by working around
it:

- The gate is `nix/scripts/releste-lint-files.sh`, mode `ascii`, wired into
  pre-commit by `nix/hooks.nix` (`ascii = lint "ascii" "";`) and therefore into
  `nix flake check` as well as `.pre-commit-config.yaml`.
- That hook is a **no-op with an exception list**:

  ```sh
  case "$f" in
    *l10n* | *i18n* | *locale* | *.po | *.ftl) ;;
    *)
      # ... check for non-ASCII bytes, FAIL non-ASCII byte:$f
      ;;
  esac
  ```

- Both `locales/en_US/editor.toml` and `locales/zh_CN/editor.toml` match the
  `*locale*` glob and are therefore **already exempt**. **No change to `nix/`,
  `.github/`, or the pre-commit configuration is required**, and none should be
  made.

Two consequences that are easy to get wrong:

- The exemption is a **path glob, not a directory rule**. A file is skipped
  because its full path contains `locale` (or `l10n`/`i18n`), which is why the
  directory must keep that name. Renaming `locales/` to `i18n-data/` would
  still work (it matches `*i18n*`), but renaming it to something like
  `translations/` would silently re-enable the ASCII check on the catalogs and
  break the build. Do not rename the directory.
- The exemption is **not** a licence for non-ASCII elsewhere. Everything under
  `crates/`, `docs/`, and the repository root - including the Rust source
  that implements the loader and this very document - stays pure ASCII per
  section 5.4. The l10n loader can process UTF-8 at run time without itself
  containing a single non-ASCII byte; that is the intended split.

Verify before committing:

```bash
# en_US must be clean.
grep -nP '[^\x00-\x7F]' locales/en_US/editor.toml && echo "FAIL: en_US is not ASCII" || echo "ok: en_US ASCII"
# zh_CN is expected to match, and is exempt.
grep -cP '[^\x00-\x7F]' locales/zh_CN/editor.toml
```

## 7.1 Fonts: why a translation can still look broken

A correct catalog is necessary but **not sufficient**. egui ships Latin and
emoji faces only, and adding a font crate is forbidden (AGENTS.md 15.1), so out
of the box every CJK label renders as tofu boxes even though the translation is
perfect.

`crates/editor/src/fonts.rs` closes that gap: at startup it searches the host's
font directories for a CJK-capable face and registers it as the *lowest-priority*
fallback for both font families. Latin text keeps using the built-in face; only
characters the default cannot draw fall through to the system font.

The font is **not embedded** - it is user-provided system infrastructure, the
same rule as `libfmod.so` (AGENTS.md 4.7). Nothing is added to a commit.

What is searched (in order): `$XDG_DATA_HOME/fonts`, `~/.local/share/fonts`,
`~/.nix-profile/share/fonts`, `/etc/profiles/per-user/$USER/share/fonts`,
`/run/current-system/sw/share/fonts`, `/usr/share/fonts`,
`/usr/local/share/fonts`, `/System/Library/Fonts`, `/Library/Fonts`,
`C:/Windows/Fonts`. A file is a candidate when its name contains a known CJK
hint (`notosanscjk`, `sourcehansans`, `wqy`, `msyh`, `pingfang`, ...).

Overrides, for a font in an unusual place or a specific face in a collection:

```bash
RELESTE_UI_FONT=/path/to/NotoSansCJK.ttc releste-editor
RELESTE_UI_FONT=/path/to/font.ttc RELESTE_UI_FONT_INDEX=2 releste-editor
```

If no font is found the editor still starts and logs a warning naming the fix.
The tofu is a missing *system* font, never a missing translation - check the log
before editing a catalog.

Face index 0 is used by default. For a `.ttc` collection that is the first face,
which is normally a shared Han face; regional variants differ only in a handful
of glyph shapes, so a Chinese label renders correctly either way.

## 8. Translation quality policy

The catalogs are not a compatibility shim and are not machine output.

- Every non-English catalog is reviewed by a **native speaker before merge**.
  See CONTRIBUTING-i18n.md for the review rule and what to look for.
- The target register for `zh_CN` is **a Celeste mapper who has used the
  original game's tooling** - terse, concrete, verb-first for actions, and
  consistent with the terminology table below. It is not a literal gloss of the
  English and it is not formal/legal register.
- Terminology is fixed centrally and must not drift between keys. The canonical
  glossary - room, tile, brush, entity, atlas, cutscene, undo/redo, inspector,
  decal - lives in [CONTRIBUTING-i18n.md](../CONTRIBUTING-i18n.md) and is the
  authority for translators.

## 9. Testing

i18n is explicitly UI-adjacent and the loader is deliberately small, so the
test surface is split:

- The loader's pure parts (parse a catalog from a string, lookup with the
  three-step chain, placeholder substitution, missing-key behaviour) are unit
  testable without a GPU and belong in `crates/editor`'s test module.
- The rendered UI itself falls under AGENTS.md section 9's exception for pure UI
  code: maintain a manual checklist instead of a screenshot test.
- CI enforces the data properties that are checkable without Rust: the ASCII
  gate (section 7), and the key-set comparison (section 5.1).
